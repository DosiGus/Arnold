## 2. Produktvision und UX-Grundsätze

Arnold soll einen Trainingsplan nicht als starre Liste behandeln.

Ein Nutzer muss seinen Plan jederzeit verändern können.

Typische Nutzerwünsche:

- „Erstelle mir einen Push/Pull/Legs-Plan.“
- „Tausche Bankdrücken gegen Kurzhantel-Bankdrücken aus.“
- „Ich möchte vier statt drei Tage trainieren.“
- „Füge Bulgarian Split Squats zum Leg Day hinzu.“
- „Verschiebe Seitheben an das Ende meines Push Days.“
- „Ändere bei Klimmzügen drei Sätze auf vier.“
- „Ich möchte wieder nach meinem alten Trainingsplan trainieren.“
- „Erstelle zusätzlich einen Oberkörper/Unterkörper-Plan.“
- „Benenne Push A in Oberkörper A um.“
- „Ich möchte meine gesamte Trainingsroutine neu gestalten.“

Der Nutzer muss diese Aktionen sowohl über ChatGPT als auch über die interaktive MCP-App auslösen können.

**Verbindliche Regeln:**

1. Trainingspläne müssen beliebige Trainingssplits unterstützen.
2. Keine feste Begrenzung auf Push/Pull/Legs.
3. Keine technische Abhängigkeit von Übungsnamen.
4. Historische Trainingsdaten bleiben erhalten.
5. Bereits aktivierte Planversionen bleiben unveränderlich.
6. Eine Planänderung muss vor der Aktivierung überprüfbar sein.
7. Der Nutzer darf eigene Übungen und eigene Trainingsstrukturen verwenden.
8. Die Bedienung soll möglichst wenig technisches Wissen voraussetzen.
9. Alle Änderungen laufen durch dieselbe Backend-Logik.
10. Kein UI-Element darf allein eine fachlich ungültige Änderung ermöglichen.

### Wichtige Designgrenze

Die Tabelle `PLAN_ITEMS` enthält momentan sowohl die Zuordnung einer Übung zu einer Session als auch Metadaten der Session.

Für V1 ist folgende Produktentscheidung zulässig:

**Ein aktivierbarer Trainingsplan muss mindestens eine Trainingseinheit mit mindestens einer gültigen aktiven Übung enthalten.**

Ein Entwurf darf während der Bearbeitung vorübergehend leere Einheiten im Editor besitzen. Diese dürfen jedoch nicht stillschweigend als dauerhaft gespeicherte Sessions ausgegeben werden, wenn das Datenschema sie nicht unterstützt.

Dokumentiere solche Grenzen und schlage notwendige spätere Schema-Migrationen separat vor.

Die aktuelle Master-Datei darf nicht verändert werden.

## 6. Arbeitsauftrag B – Lebenszyklus der Trainingspläne

Definiere eine verbindliche State Machine.

Bestehende Statuswerte:

```text
draft
active
archived
```

### Erlaubte Übergänge

```text
draft -> active

active -> archived

draft -> archived
```

Die letzte Variante kann verwendet werden, um einen nicht mehr benötigten Entwurf zu verwerfen.

Eine archivierte oder aktive Version darf nicht wieder als bearbeitbarer Draft verwendet werden.

### Verbindliche Regeln

1. Ein aktivierter Plan wird nicht mehr inhaltlich verändert.
2. Änderungen an einem aktiven Plan erzeugen eine neue Draft-Version.
3. Bereits abgeschlossene Workouts bleiben an ihrer historischen Planversion.
4. Ein Planwechsel darf keine vorhandenen Trainingsdaten überschreiben.
5. Eine archivierte Version bleibt lesbar.
6. Alte Pläne können als Grundlage einer neuen Draft-Version wiederverwendet werden.
7. Das Zurückkehren zu einem früheren Plan erstellt eine neue aktivierbare Version beziehungsweise einen neuen Aktivierungsstand.
8. Der ursprüngliche archivierte Datensatz bleibt unverändert.

### Entscheidungsregel für V1

Innerhalb eines persönlichen Arnold-Trackers darf es maximal **eine aktive Trainingsplanversion** gleichzeitig geben.

Es dürfen jedoch beliebig viele archivierte Versionen und mehrere Entwürfe existieren.

Ein späteres Produktupdate kann mehrere parallele aktive Pläne unterstützen.

Implementiere dafür keine unnötigen Sonderwege im MVP.

## 7. Arbeitsauftrag C – Versionierungsengine

Implementiere eine sichere Versionierung.

Empfohlener Service:

`PlanVersioningService`

### Beispiel

Der Nutzer hat folgenden Plan:

```text
Plan Family: PF_001
Plan Version: PV_001
Version Number: 1
Status: active
```

Er möchte Bankdrücken durch Kurzhantel-Bankdrücken ersetzen.

Arnold erstellt:

```text
Plan Family: PF_001
Plan Version: PV_002
Version Number: 2
Status: draft
```

Die neue Version basiert auf der alten Version, ist aber unabhängig bearbeitbar.

### Regeln

- Neue `plan_version_id` erzeugen.
- Die `plan_family_id` bei einer Änderung derselben Routine beibehalten.
- Versionsnummer eindeutig innerhalb einer Planfamilie vergeben.
- Alle Planpositionen für die neue Version mit neuen `plan_item_id`-Werten erstellen.
- Historische Planpositionen nicht überschreiben.
- Exercise-IDs unverändert referenzieren.
- Session-Identitäten bewusst behandeln.

### Session-ID-Strategie

Für V1 gilt:

- Bei einer unverändert fortgeführten Trainingseinheit darf `session_id` innerhalb derselben Planfamilie stabil bleiben.
- Eine neu hinzugefügte Trainingseinheit erhält eine neue ID.
- Das Duplizieren einer Trainingseinheit erzeugt eine neue Session-ID.
- Eine neue, unabhängige Planfamilie erhält eigene Session-IDs.

Änderungen am Session-Namen dürfen bestehende historische Anzeigen nicht rückwirkend verändern.

Die `session_name_snapshot`-Information in WORKOUTS bleibt erhalten.

### Versionskonflikte

Falls zwei Änderungen parallel versuchen, dieselbe Versionsnummer oder denselben Draft zu verändern, muss die Engine den Konflikt erkennen.

Keine doppelten Versionsnummern innerhalb einer Planfamilie zulassen.

Nutze Idempotenz und Schreibkoordination aus Task 004.

Ganzkörper A

## 9. Arbeitsauftrag E – Trainingseinheiten bearbeiten

Implementiere Operationen für:

```text
add_session
rename_session
reorder_sessions
duplicate_session
remove_session
```

### Hinzufügen

Neue Session-ID erzeugen.

Der Nutzer kann beispielsweise einen vierten Trainingstag ergänzen.

### Umbenennen

Alle zur Session gehörenden Planpositionen innerhalb des Drafts konsistent aktualisieren.

Keine historischen Workouts verändern.

### Reihenfolge

Session-Reihenfolge eindeutig speichern.

Keine doppelten oder widersprüchlichen Reihenfolgewerte zulassen.

### Duplizieren

Beim Duplizieren einer Einheit:

- Neue Session-ID erzeugen.
- Neue Planposition-IDs erzeugen.
- Vorhandene Exercise-IDs referenzieren.
- Ziele und Ausführungen übernehmen.
- Originaleinheit unverändert lassen.

### Entfernen

Eine Session aus dem aktuellen Draft entfernen beziehungsweise fachlich deaktivieren.

Für bereits aktive oder archivierte Planversionen dürfen keine Planpositionsdaten gelöscht werden.

Wenn das vorhandene Datenmodell eine Änderung nicht dauerhaft darstellen kann, muss dies ausdrücklich als nicht unterstützt gekennzeichnet werden.

## 10. Arbeitsauftrag F – Übungen innerhalb eines Plans bearbeiten

Implementiere folgende Operationen:

```text
add_plan_exercise
replace_plan_exercise
remove_plan_exercise
reorder_plan_exercises
update_plan_exercise_targets
update_plan_exercise_execution
```

### A – Neue Übung hinzufügen

Beispiel:

„Füge Seitheben zu meinem Push Day hinzu.“

Verhalten:

1. Session identifizieren.
2. Exercise-ID ermitteln.
3. Bei Mehrdeutigkeit keine willkürliche Übung auswählen.
4. Planposition erstellen.
5. Standardausführung aus dem Übungskatalog übernehmen.
6. Bearbeitung innerhalb des Drafts speichern.
7. Planrevision erhöhen.

### B – Übung austauschen

Beispiel:

„Ersetze Langhantel-Bankdrücken durch Kurzhantel-Bankdrücken.“

Die neue Übung bekommt eine neue Planposition-ID, sofern die bisherige Planposition bereits eine andere Bewegungsvariante bezeichnet.

Die alte Position der historischen Planversion bleibt erhalten.

Nicht allein den Textnamen überschreiben.

### C – Übung entfernen

Eine Übung wird aus dem neuen Draft entfernt beziehungsweise deaktiviert.

Der Übungskatalog und historische Workouts bleiben erhalten.

### D – Reihenfolge ändern

Beispiel:

„Mach Seitheben zur letzten Übung.“

Die Reihenfolge muss deterministisch gespeichert werden.

### E – Trainingsziele ändern

Unterstütze:

- Zielsätze
- Wiederholungsminimum
- Wiederholungsmaximum
- Zielgewicht
- Gewichtsdefinition
- Ausführung
- Anzahl der Hanteln beziehungsweise Geräte
- Pause
- Notiz

### Validierung

- `rep_min <= rep_max`.
- Satzanzahl ist eine gültige positive Ganzzahl.
- Reihenfolgewerte sind gültig.
- Negative Gewichte nicht ohne fachliche Begründung zulassen.
- Zielgewicht darf bei bestimmten Übungsarten fehlen.
- Belastungsdefinition muss zur Übungsvariante passen.
- Unterschiedliche Ausführungen müssen ausdrücklich gespeichert werden.

### Pflichtregel

Alle Änderungen an aktivierten Planversionen müssen über eine neue Draft-Version laufen.

## 11. Arbeitsauftrag G – Planentwürfe bearbeiten

Implementiere:

`update_plan_draft`

Ein Draft kann über mehrere UI-Interaktionen verändert werden.

### Anforderungen

- Draft-ID beziehungsweise Planversions-ID erforderlich.
- Erwartete `row_revision` erforderlich.
- Konflikterkennung bei parallelen Änderungen.
- Strukturierte Validierung.
- Aktualisierungszeitpunkt speichern.
- Revision erhöhen.
- Kein Schreiben in aktive oder archivierte Versionen.
- Audit-Ereignis speichern.
- Idempotente Wiederholungen unterstützen.

### Bearbeitungsstrategie

Bevorzuge typisierte Änderungsoperationen gegenüber dem ungeprüften Überschreiben eines gesamten Tabellenbereichs.

Für komplexe Änderungen darf ein vollständiger neuer Draft-Zustand übertragen werden, sofern:

- Die vorherige Revision geprüft wurde.
- Alle Referenzen validiert wurden.
- Die Änderung vollständig als zusammengehörige Operation behandelt wird.
- Kein historischer Datensatz überschrieben wird.

### Wichtig

Google Sheets besitzt keine transaktionalen Datenbankconstraints.

Die Anwendung muss Schreibkonflikte durch die vorhandene serverseitige Koordination behandeln.

Die verbleibenden Risiken durch externe manuelle Änderungen müssen dokumentiert werden.

## 12. Arbeitsauftrag H – Planvalidierung

Implementiere:

`validate_training_plan`

Diese Funktion muss vor einer Aktivierung ausgeführt werden.

### Prüfungen

1. Existiert die Planversion?
2. Ist die Version ein Draft?
3. Existiert mindestens eine gültige Einheit?
4. Existiert mindestens eine aktive Übung im gesamten Plan?
5. Sind alle referenzierten Übungen gültig?
6. Sind alle Session-IDs konsistent?
7. Sind die Reihenfolgen konsistent?
8. Sind alle Satzanzahlen gültig?
9. Sind Wiederholungsbereiche gültig?
10. Sind Zielgewichte und Gewichtskonventionen gültig?
11. Sind Ausführungen valide?
12. Gibt es unzulässige doppelte Planposition-IDs?
13. Gibt es nicht darstellbare Strukturen?
14. Passt der Plan zur bestehenden Schema-Version?

### Ergebnis

Liefere strukturierte Ergebnisse.

Beispiel:

```json
{
  "valid": false,
  "errors": [
    {
      "code": "INVALID_REP_RANGE",
      "plan_item_id": "item_004",
      "message": "Das Wiederholungsminimum darf nicht größer als das Maximum sein."
    }
  ],
  "warnings": []
}
```

Unterscheide zwischen:

- Blockierenden Fehlern.
- Fachlichen Hinweisen.
- Optionalen Empfehlungen.

Eine niedrige oder hohe Anzahl von Trainingstagen ist nicht automatisch ein technischer Fehler.

Trainingswissenschaftliche Empfehlungen sind nicht Teil der Speicherungsgarantie.

## 13. Arbeitsauftrag I – Planaktivierung

Implementiere:

`activate_training_plan`

Das ist eine besonders kritische Operation.

### Ziel

Ein bestätigter Draft wird zur aktiven Trainingsplanversion.

Die bisher aktive Planversion wird archiviert.

### Voraussetzungen

- Nutzeridentität ist in produktivem Betrieb geprüft.
- Der Draft existiert.
- Der Draft ist gültig.
- Die erwartete Revision stimmt.
- Eine ausdrückliche Bestätigung der konkret angezeigten Draft-Version liegt vor.
- Kein konkurrierender Aktivierungsvorgang ist offen.
- Die Operation ist idempotent.

### Aktivierungsschritte

1. Aktuelle aktive Planversion identifizieren.
2. Draft anhand der aktuellen Revision validieren.
3. Bestätigung gegen dieselbe Planversion und Revision prüfen.
4. Bisherige aktive Version archivieren.
5. `retired_at_utc` setzen.
6. Neuen Draft aktivieren.
7. `activated_at_utc` setzen.
8. Revisionsnummern aktualisieren.
9. Ergebnis verifizieren.
10. Audit-Ereignis speichern.

### Konsistenz

Es darf nicht dauerhaft zu zwei aktiven Plänen kommen.

Wenn die Aktivierung nicht sicher abgeschlossen werden kann, muss Arnold den Zustand prüfen und gegebenenfalls in einen kontrollierten Fehlerzustand wechseln.

Keine positive Erfolgsmeldung bei unbestätigter Speicherung.

### Bereits laufende Workouts

Ein vor der Planaktivierung begonnenes Workout bleibt mit seiner ursprünglich ausgewählten Planversion verbunden.

Eine spätere Planänderung darf nicht die Übungen eines bereits laufenden Workouts unbemerkt ersetzen.

### Bestätigung

Eine erfolgreiche technische Draft-Validierung ist keine Nutzerbestätigung.

Die Bestätigung muss sich auf eine konkrete Planversion und Revision beziehen.

Im Testbetrieb dürfen explizite simulierte Bestätigungsereignisse verwendet werden.

Die endgültige Identitätsbindung erfolgt mit der produktiven Authentifizierung.

## 14. Arbeitsauftrag J – Historische Pläne und Wiederherstellung

Implementiere lesende und erzeugende Funktionen für die Planhistorie.

Mindestens:

```text
get_training_plan
list_training_plans
get_plan_history
compare_plan_versions
clone_plan_version
```

### Planhistorie

Der Nutzer soll sehen können:

- Aktueller Plan.
- Frühere Planversionen.
- Zeitpunkt der Aktivierung.
- Zeitpunkt der Archivierung.
- Unterschiede zur aktuellen Version.

### Beispiel

```text
Version 1:
Push / Pull / Legs

Version 2:
Push / Pull / Legs angepasst

Version 3:
Oberkörper / Unterkörper
```

### Vergleich

Eine Vergleichsfunktion soll Änderungen erkennen:

- Übungen hinzugefügt.
- Übungen entfernt.
- Übungen ersetzt.
- Reihenfolge geändert.
- Zielsätze verändert.
- Wiederholungsbereiche verändert.
- Gewichtsziele verändert.
- Ausführungen geändert.
- Trainingseinheiten hinzugefügt oder entfernt.
- Trainingseinheiten umbenannt.

Die Ausgabe soll sowohl maschinenlesbar als auch für eine übersichtliche UI geeignet sein.

### Alte Version erneut verwenden

Wenn ein Nutzer eine alte Version wiederverwenden möchte:

1. Archivierte Version lesen.
2. Neuen Draft auf ihrer Grundlage erstellen.
3. Neue IDs für die Draft-Version und ihre Planpositionen vergeben.
4. Nutzer kann Anpassungen vornehmen.
5. Draft bestätigen und aktivieren.
6. Historische Originalversion unverändert erhalten.

- Sinnvolle MCP-Tool-Annotationen.
- Fehlercodes.
- Idempotenz bei schreibenden Operationen.
- Benutzerbezogene Autorisierung im späteren Produktbetrieb.

### API-Design

Vermeide unnötig viele einzelne Tools für jede kleine Planänderung.

Die Funktionen zum Hinzufügen, Verschieben oder Ersetzen von Übungen können als typisierte Operationen innerhalb von `update_plan_draft` implementiert werden.

Beispielhafte Änderungsobjekte:

```json
{
  "type": "replace_exercise",
  "session_id": "session_push",
  "plan_item_id": "item_001",
  "new_exercise_id": "ex_incline_db_press"
}
```

Die genaue API muss konsistent und eindeutig sein.

### Schreibschutz

Die Tools dürfen keine produktiven Google-Sheets-Schreibzugriffe ermöglichen, solange Task 004 und die spätere Nutzerautorisierung nicht vollständig abgesichert sind.

## 18. Arbeitsauftrag N – Planverwaltung und Workout-Logging integrieren

Die Planverwaltung muss mit Task 004 zusammenarbeiten.

### Beispiel

Ein Nutzer trainiert nach:

```text
Plan V1:
Push / Pull / Legs
```

Er absolviert ein Push-Workout.

Anschließend ersetzt er Bankdrücken durch Kurzhantel-Bankdrücken.

Arnold erzeugt:

```text
Plan V2:
Push / Pull / Legs
```

### Ergebnis

Das alte Workout referenziert weiterhin Plan V1.

Neue Workouts können Plan V2 verwenden.

Die alten Bankdrücken-Sätze bleiben unverändert erhalten.

Die neue Übung bekommt eine eigene Exercise-ID beziehungsweise bestehende eindeutige Übungsreferenz.

### Anforderungen

1. Workout-Erstellung nutzt die aktuell aktivierte Planversion.
2. Spontane Workouts bleiben möglich.
3. Planänderungen erzeugen keine Veränderungen an vergangenen Workout-Datensätzen.
4. Laufende Workouts behalten ihre ursprüngliche Planreferenz.
5. Änderungen an Zielgewichten überschreiben keine tatsächlich geloggten Gewichte.
6. Workout-Logger kann neue Planinformationen laden.
7. Analytics über mehrere Planversionen hinweg bleibt funktionsfähig.

### Optionaler Komfort

Beim Start eines Workouts können geplante Übungen als Vorschläge angezeigt werden.

Diese Vorschläge sind noch keine tatsächlich absolvierten Sätze.

Erst nach ausdrücklicher Erfassung dürfen sie als Workout-Sets gespeichert werden.

## 19. Arbeitsauftrag O – Vorbereitungen für das Onboarding

Task 006 implementiert später das eigentliche Onboarding.

Task 005 soll die dafür nötigen Planfunktionen vorbereiten.

### Zukünftiger Ablauf

```text
Neuer Nutzer
     |
     v
Onboarding-Fragen
     |
     v
Trainingsprofil
     |
     v
KI-generierter Planvorschlag
     |
     v
TrainingPlanEditor
     |
     v
Nutzer überprüft und bearbeitet
     |
     v
Plan bestätigen
     |
     v
Google OAuth / Tracker erstellen
     |
     v
Plan aktivieren
     |
     v
Arnold Dashboard
```

### Verbindliche Vorbereitungen

Der Planservice soll vollständige, strukturierte Planvorschläge entgegennehmen können.

Er darf jedoch nicht voraussetzen, dass diese Vorschläge ausschließlich von einer KI erzeugt werden.

Unterstützte Quellen:

- Manuelle Erstellung.
- Vorhandener Nutzerplan.
- Strukturierter KI-Vorschlag.
- Kopie einer bisherigen Planversion.

### Wichtige Regel

Die KI-generierte Planstruktur ist zunächst nur ein Vorschlag.

Sie darf nicht ohne ausdrückliche Nutzerbestätigung als aktiver Plan gespeichert werden.

### Aufgabengrenze

Noch keine Onboarding-State-Machine implementieren.

Noch keine eigenständige KI-Plan-Generierung implementieren.

Noch kein Google OAuth.

Noch keine automatische Erstellung persönlicher Tracker-Dateien.

Der fertige Planeditor muss jedoch aus dem künftigen Onboarding heraus aufgerufen werden können.
