# ARNOLD – DEVELOPMENT TASK 003
## Dashboard Integration, Analytics API & MCP UI Modernization

Du arbeitest als Senior Full-Stack Engineer, MCP Apps Developer und Frontend Architect am Projekt **Arnold**.

Arnold ist eine KI-gestützte Fitness-Anwendung innerhalb von ChatGPT. Das Produkt kombiniert einen MCP-Server, eine interaktive React-Oberfläche, eine eigene Analytics Engine und Google Sheets als anfängliche Rohdatenquelle.

**Projektsteuerung:** Dieser Auftrag ist Teil einer übergeordneten Produktentwicklung. Implementiere ausschließlich den definierten Umfang und liefere anschließend einen vollständigen technischen Abschlussbericht.

## 4. Arbeitsauftrag B – Neue Dashboard-Datenpipeline

Implementiere die folgende Datenpipeline:

```text
Arnold Google Sheets
        |
        v
ArnoldSheetsReadAdapter
        |
        v
ArnoldDataset
        |
        v
Arnold Analytics Engine
        |
        v
ArnoldDashboardAnalytics
        |
        v
MCP Tools
        |
        v
Arnold React UI
```

### Anforderungen

1. Google Sheets wird ausschließlich serverseitig gelesen.
2. Die UI bekommt keine Google-Zugangsdaten.
3. Die UI greift nicht direkt auf Google Sheets zu.
4. Alle Berechnungen erfolgen über die Analytics Engine.
5. Das Frontend führt keine eigene widersprüchliche Metrikberechnung durch.
6. Alle API-Ergebnisse werden mit Zod validiert.
7. Keine synthetischen Demo-Daten als Ersatz für fehlende echte Daten verwenden.
8. Ungültige oder fehlende Kennzahlen werden transparent dargestellt.
9. Die UI muss mit einer vollständig leeren Trainingshistorie funktionieren.

### Architekturentscheidung

Verwende die fertiggestellten Ergebnisstrukturen aus Task 002 als Grundlage.

Falls deren konkrete Feldnamen vom ursprünglichen Planungsvorschlag abweichen, übernehme den tatsächlich implementierten und getesteten Vertrag.

Erfinde nicht parallel ein zweites Analytics-Modell.

Falls nötig, implementiere eine kleine Presenter- oder ViewModel-Schicht für die UI.

## 5. Arbeitsauftrag C – MCP-Tools für das Dashboard

Die bisherigen MCP-Tools sind:

- `show_arnold_dashboard`
- `get_dashboard_data`
- `get_workouts`
- `get_exercise_progress`

Außerdem existieren Demo-spezifische Schreib- und Reset-Tools.

### Ziel

Die bestehenden lesenden Tools sollen künftig auch die neue Arnold-Datenstruktur unterstützen.

### `show_arnold_dashboard`

Soll weiterhin das interaktive Arnold-Dashboard innerhalb von ChatGPT öffnen.

Anforderungen:

- Korrekten MCP-App-Ressourcenverweis liefern.
- Aktuelle Datenquelle erkennen.
- UI mit gültigem initialem Zustand öffnen.
- Kein Onboarding simulieren.
- Bei leerem Tracker eine sinnvolle leere Oberfläche anzeigen.

### `get_dashboard_data`

Soll standardisierte Kennzahlen liefern.

Mindestens:

- Anzahl Workouts
- Trainingstage
- Trainingshäufigkeit
- Satzanzahl
- Trainingsvolumen
- Wochenentwicklung
- Persönliche Bestleistungen
- Informationen zum aktiven Trainingsplan
- Datenqualitätsstatus

Die Ergebnisse stammen aus der Analytics Engine.

### `get_workouts`

Soll Trainingshistorien abrufen.

Unterstütze Filter nach:

- Zeitraum
- Plan-ID beziehungsweise Planversion
- Trainingseinheit
- Status

Keine zwingende Beschränkung auf Push/Pull/Legs.

Unterstütze eine begrenzte Ergebnismenge beziehungsweise Pagination, wenn die Datenmenge dies erfordert.

### `get_exercise_progress`

Soll den Fortschritt einer Übung abrufen.

Unterstütze:

- `exercise_id`
- Zeitraum
- Auswertungsmetrik
- Vergleichbare Ausführungsvariante, falls erforderlich

Metriken dürfen nicht zwischen inkompatiblen Ausführungen vermischt werden.

### Kompatibilität

Behalte bestehende Tool-Namen bei, soweit das ohne widersprüchliche Output-Schemas möglich ist.

Wenn ein inkompatibler Output-Vertrag erforderlich wird, verwende eine ausdrücklich versionierte neue Schnittstelle.

Vermeide stillschweigende Änderungen, die bestehende Clients beschädigen.

Die alten Demo-Tools müssen weiterhin im Demo-Modus funktionieren.

## 7. Arbeitsauftrag E – Dashboard-Übersicht

Modernisiere die vorhandene Übersichtsseite.

### 7.1 KPI-Bereich

Zeige mindestens:

- Trainingseinheiten gesamt
- Trainingstage im ausgewählten Zeitraum
- Trainingstage beziehungsweise Workouts pro Woche
- Anzahl gültiger Arbeitssätze
- Trainingsvolumen mit eindeutigem Kennzahlentyp
- Aktiver Trainingsplan

Wenn Kennzahlen aufgrund fehlender Daten nicht berechenbar sind, zeige nicht einfach `0`.

Verwende stattdessen beispielsweise einen neutralen Platzhalter und eine kurze Erklärung.

### 7.2 Wochenentwicklung

Zeige einen interaktiven Verlauf mit:

- Workouts pro Woche
- Trainingstagen pro Woche
- Optional nominalem Trainingsvolumen

Unterstütze geeignete Zeitraumfilter.

### 7.3 Letzte Trainingseinheiten

Zeige:

- Datum
- Name der Trainingseinheit
- Anzahl Übungen
- Anzahl Sätze
- Optional Trainingsvolumen

Ein Klick auf eine Einheit soll ihre Details öffnen.

### 7.4 Persönliche Bestleistungen

Zeige eine Auswahl relevanter PRs.

Kennzeichne eindeutig:

- Übung
- Gewicht
- Ausführung, soweit nötig
- Wiederholungen
- Datum
- PR-Typ

Mische keine inkompatiblen Lastdefinitionen.

### 7.5 Datenquelle

Zeige einen kleinen, verständlichen Datenquellenhinweis.

Beispiele:

- „Demo-Daten“
- „Arnold · Google Sheets“
- „Master-Vorlage · Noch keine Workouts“

Wenn der Server im Master-Template-Modus arbeitet, darf die Anwendung diesen Zustand nicht als vollständig eingerichtetes persönliches Nutzerkonto darstellen.

## 8. Arbeitsauftrag F – Workout-Historie

Implementiere die Anzeige einer beliebigen Trainingshistorie.

### Anforderungen

- Keine festen Splits voraussetzen.
- Namen von Trainingseinheiten dynamisch übernehmen.
- Spontane Workouts ohne Planreferenz unterstützen.
- Historische Planversionen berücksichtigen.
- Unvollständige oder stornierte Workouts klar unterscheiden.
- Sätze in einer nachvollziehbaren Reihenfolge anzeigen.
- Die tatsächlichen Eingaben unverändert darstellen.

### Beispiel

Ein Workout kann aus folgenden Daten bestehen:

```text
Workout:
  20.10.2026
  Oberkörper A

Übung:
  Bankdrücken

  Satz 1: 60 kg × 10
  Satz 2: 70 kg × 8
  Satz 3: 70 kg × 7

Übung:
  Rudern einarmig

  Rechts: 20 kg × 10
  Links: 20 kg × 10
```

Die Darstellung darf aus mehreren Satzdatensätzen eine verständliche Übungskarte bilden.

Dabei müssen Links/Rechts-Informationen, Gewichtsdefinitionen und Ausführungsarten erhalten bleiben.

### Historische Daten

Wenn der Nutzer eine Übung später aus seinem Trainingsplan entfernt, muss sie weiterhin in alten Workouts erscheinen.

Die UI darf historische Übungsdaten nicht ausschließlich aus dem aktuell aktiven Plan rekonstruieren.

## 9. Arbeitsauftrag G – Trainingsfortschritt

Die bestehende Fortschrittsansicht verwendet Recharts.

Behalte Recharts bei.

### Anforderungen

Der Nutzer kann:

1. Eine Übung auswählen.
2. Einen Zeitraum auswählen.
3. Eine Kennzahl auswählen.
4. Die Entwicklung betrachten.

### Unterstützte Kennzahlen

Soweit durch Task 002 verfügbar:

- Maximale vergleichbare Trainingslast
- Wiederholungen
- Nominales Trainingsvolumen
- Geschätztes 1RM
- Trainingshäufigkeit pro Übung

### Visualisierung

Für Verlaufskurven:

- Echte Messpunkte verwenden.
- Keine erfundenen Daten ergänzen.
- Fehlende Werte nicht als null darstellen, wenn sie unbekannt sind.
- Datumswerte chronologisch sortieren.
- Bei mehreren Workouts am selben Tag die definierte Aggregationsregel berücksichtigen.
- Vergleichbarkeit von Ausführungen respektieren.

### Beispiel

Bankdrücken:

```text
01.10.2026: 70 kg × 8
08.10.2026: 70 kg × 10
15.10.2026: 75 kg × 8
```

Das Dashboard soll daraus eine sinnvolle Entwicklung darstellen.

Die eigentliche Berechnung findet vollständig im Backend statt.

### Besondere Fälle

Wenn eine Übung bisher nur einmal geloggt wurde, muss die UI auch einen einzelnen Messpunkt korrekt darstellen.

Wenn eine Übung noch nie geloggt wurde, zeige einen passenden Leerzustand.

## 10. Arbeitsauftrag H – Ausführungsarten verständlich darstellen

Arnold unterstützt:

- Beidarmige beziehungsweise beidseitige Übungen
- Einarmige Übungen
- Einbeinige Übungen
- Alternierende Übungen
- Gewicht pro Hantel
- Gesamtgewicht
- Maschinengewicht
- Zusatzgewicht
- Unterstützte Körpergewichtsübungen

### UX-Regeln

Ein Nutzer soll nicht mit internen Datenbankbegriffen wie `per_implement` konfrontiert werden.

Verwende verständliche Beschriftungen.

Beispiele:

| Technischer Wert | UI-Anzeige |
|---|---|
| `per_implement` | kg pro Hantel |
| `total` | Gesamtgewicht |
| `machine_display` | Maschinenanzeige |
| `added` | Zusatzgewicht |
| `assistance` | Unterstützung |
| `unilateral` | Einseitig |
| `alternating` | Abwechselnd |
| `left` | Links |
| `right` | Rechts |

Die UI muss die tatsächlich gespeicherte Ausführung anzeigen können, auch wenn sie vom Standard der Übung abweicht.

### Technische Regel

Erzeuge eine zentrale Formatierungsfunktion für Gewichtsangaben.

Nicht in unterschiedlichen Komponenten jeweils eigene Interpretationslogik implementieren.

## 11. Arbeitsauftrag I – Datenzustände und Fehlerbehandlung

Implementiere klare Zustände für:

1. Daten werden geladen.
2. Erfolgreich geladen.
3. Keine Workouts vorhanden.
4. Keine Übungen vorhanden.
5. Datenquelle nicht erreichbar.
6. Google-Autorisierung fehlt.
7. Datenstruktur inkompatibel.
8. Teilweise ungültige Daten.
9. Ein veralteter Snapshot liegt vor.

### Leerer Tracker

Unsere neue Arnold-Masterdatei enthält aktuell:

- Sechs Tabellen.
- Einen Übungskatalog.
- Noch keine individuellen Workouts.

Deshalb soll der neue Dashboard-Modus beim erstmaligen Öffnen ungefähr folgende Inhalte zeigen:

**„Willkommen bei Arnold“**

„Deine Trainingsdatenbasis ist bereit. Sobald du dein erstes Training erfasst, siehst du hier deine Fortschritte.“

Diese Meldung ist nur ein vorläufiger Leerzustand.

Keine künstlichen Beispiel-Workouts anzeigen.

Keinen vermeintlich funktionierenden Onboarding-Button einbauen, solange der Onboarding-Prozess noch nicht existiert.

### Fehlerbehandlung

Wenn Google Sheets nicht erreichbar ist:

- Keine Demo-Daten als Ersatz anzeigen.
- Keine veralteten Werte als frisch deklarieren.
- Verständliche Fehlermeldung anzeigen.
- Gegebenenfalls eine Aktion zum erneuten Laden anbieten.

Wenn alte zwischengespeicherte Werte angezeigt werden, müssen sie ausdrücklich als veraltet gekennzeichnet sein.

## 13. Arbeitsauftrag K – Performance

Arnold soll langfristig auch mit mehreren Jahren Trainingshistorie funktionieren.

Vermeide deshalb unnötige Vollabfragen bei jeder Interaktion.

### Grundregeln

- Dashboard-Kennzahlen aggregiert übertragen.
- Workout-Details bei Bedarf laden.
- Fortschrittsdaten nach Übung und Zeitraum filtern.
- Datumsfilter serverseitig berücksichtigen.
- Große Arrays nicht unnötig vervielfachen.
- Wiederholte Requests sinnvoll zusammenfassen.
- Die UI nicht bei jedem Filterwechsel vollständig neu initialisieren.

Für diesen Auftrag sind keine komplexen Caching-Dienste notwendig.

Baue jedoch eine Architektur, in der später serverseitiges Caching ergänzt werden kann.

### Wichtig

Ein neues Cache darf nicht dazu führen, dass nach einem erfolgreichen Schreibvorgang veraltete Daten angezeigt werden.

Schreibvorgänge gehören zwar nicht zum aktuellen Auftrag, die spätere Integration muss aber architektonisch berücksichtigt werden.
